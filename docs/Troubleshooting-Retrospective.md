## BW-01 · 资产“看起来对”不等于应用还原

- **现象**：用户批准设计图后，实际画纸、昆虫和场景仍出现旧资产、塑料质感、穿模及较大视觉差距。
- **早期不足**：概念图表现被过早当作实现目标已具备；资产来源、实际导出结果和运行包之间缺少清晰证据链。
- **调整**：先生成真实 Blender/GLB，实际渲染自查，再请用户确认；批准后接入，运行目录删除旧模型，APK 按哈希逐文件核对。昆虫四模型和二十段动画锁定批准身份；Stage 优化使用明确派生清单。
- **结论**：用户已批准后续真实资产渲染；这不代表头显灯光、水面、动画和性能已通过。保留可编辑源文件、导出哈希、反射来源和设备结果，分层验收。
- **依据**：[V3 实施](V3-Implementation-Results.md)、[1.0.9 资产核对](Stage-109-Asset-Verification.json)。
- **绿色森林再设计（2026-10-20）**：用户确认概念方向后，先制作独立真实 GLB 试做。四轮检查依次发现草环/亮度、木叶相交、叶片与岸石相交，再修正并扩大到 39 组实际三角形检查；几何检查通过不代表视觉通过。当前水面、远景清晰度及衔接仍未达到概念，明确不接入应用。4K 全景升级请求实际仍输出 1774×887，失败结果保留，不能将提示中的目标分辨率当结果。见 [试做自查](../assets-src/emerald-forest-review/README.md)。
- **背景导出边界**：试做验证发现纯 Blender Emission 导出仍是 lit PBR + emissiveTexture，并非 `KHR_materials_unlit`。明确转换声明后重导入与格式校验通过；这不是已安装星空故障的证据，也不替代 PICO 深度/阴影验证。

## BW-02 · 1.0.6 画板按钮无法点击

- **现象**：新画纸、预览、进入 Stage 等按钮失效。
- **定位与处理**：独立预览层覆盖 Compose 画板，空间命中关系不统一；改为 SpatialView 内的原生 AttachmentPanel，预览只响应昆虫碰撞体。
- **验证**：用户确认按钮恢复；语义测试覆盖新画纸确认/取消、预览、物种切换、作品册。语义点击不替代手指和眼手体验。
- **复盘**：空间输入问题先查容器叠层、命中归属、事件消费，不先归因于普通按钮监听器。
- **依据**：[1.0.7](Studio-107-Results.md)。

## BW-03 · 画具不可见、灰条与空间随动

| 尝试 | 结果 |
| --- | --- |
| 独立 WindowContainer | 拉近主画板时不能一起移动，不符合直接手指绘画 |
| SpatialView 右侧 AttachmentPanel | 候选包用户反馈画具不可见 |
| 原生右侧 Subwindow | 可见并随动，但出现右侧灰条 |
| 内容去掉 320 dp 宽度限制，铺满 SDK 的 360 dp 容器 | 原生边界与内容均为 720×1680 像素；灰条消失 |
| 围绕贴近画板的边缘向内旋转 25° | 用户确认“都正常，角度合适” |

结论：应使用适合侧边附属界面的原生容器，并检查实际容器尺寸，不能只按内容尺寸推测灰边原因。依据：[1.0.7](Studio-107-Results.md)、[1.0.8](Studio-108-Results.md)。

## BW-04 · TopBar 四图标一起高亮、首项行为不一致

- **原因**：为缩短导航，将四个可点击项放进同一个原生 TabBar item；外层还绑定“更多”，造成共享 Hover 与点击祖先。
- **修正**：每种昆虫独占原生 item；四项统一直接换画纸，未来增加种类时才增加单独“更多”；缩小品牌和图标尺寸控制总宽。
- **验证**：旧版专项语义检查失败，新版通过；用户确认各自高亮正常。
- **复盘**：空间原生组件的项目级输入/高亮边界要与视觉按钮一一对应，不能只靠内部普通 Compose clickable 划分。
- **依据**：[1.0.8](Studio-108-Results.md)。

## BW-05 · 星空纹理已加载但背景一直黑色

**环境**：PICO Spatial 6.1.0，Full Stage，1.0.9 及诊断包，原生 Unlit OPAQUE 天空球。用户真机观察作为可见性证据。

| 次序 | 改变/检查 | 实际结果 |
| --- | --- | --- |
| 早期照明修正 | 配置天空 IBL、主光与补光，校正水面反射 | 植物照明有所变化；用户继续反馈黑天空，未解决背景可见性 |
| 1.0.9 | 换明亮星空、匹配 IBL；天空取消面剔除，仍关闭深度写入 | 日志证实 PNG 1774×887 加载成功；用户确认仍黑 |
| 诊断 A | 只将天空球半径 32 m 改为 12 m | 用户确认仍黑；缩半径不能解释/解决此故障 |
| 诊断 B | 保持 12 m，仅 `setDepthWrite(false)` 改为 `true` | 用户明确确认“星空出现了” |

**结论**：已证实此设备/版本的这套不透明天空绘制配置依赖开启深度写入。底层原生渲染器为何如此尚无证据，不能进一步宣称已证明某个深度预处理缺陷，也不能把半径修改说成已确认根因。

**保留与回归**：开启深度写入并保留深度测试，近处叶/虫仍应遮挡天空；检查四个方向、地平线/水面衔接、重入 Stage、坐姿/站姿。对 12 m 之外实体的遮挡需随布局检查。该用户确认只针对星空出现，不包含帧率或全部画质。

## BW-06 · 降面后仍卡顿，甚至更差

- **已知事实**：Stage 从 494,775 降到 251,260 三角面，GLB 从 52.13 MB 降到 32.88 MB；用户实际反馈仍严重卡顿。
- **日志线索**：两只昆虫准备并显示后，应用帧回调 P50 曾达到 22–111 ms，P95 约 133 ms；本地逻辑约 1.0–1.7 ms。该间隔不是 GPU 或合成器 FPS，但证实“面数少即流畅”的判断不成立。
- **进一步盘点**：瓢虫 139、独角仙 150 个图元提交单元；加上材质、骨骼、阴影、双眼及原生 Hover，成本不能只用总面数表示。每帧还反复写入不变的透明度/动画速度，可能触发原生层工作，尚需隔离测量。
- **工具尝试**：`pico-cli perf` 起初提示 0.2.0 工具未安装；后在本机 CLI 的 vendor 包中找到对应工具，使用项目 `.work` 与进程内入口覆盖运行，无需修改全局插件配置。首次采样只有系统环境帧率、应用 CPU 为 0，判定不是有效 Stage 基线，结果不用于性能结论。
- **透明度试验**：保持图像/模型/路线不变，仅跳过重复的 `OpacityControllerComponent.opacity=1` 写入。用户反馈“没加载昆虫之前不卡，加载后仍然很卡”，故该修改未解决主要卡顿；不能据此宣称性能改善。下一步重点隔离昆虫显示后的渲染/动画成本，尚不能仅凭此判断是面数或 GPU 瓶颈。
- **有效性能对照**：4 只昆虫、佩戴状态下录制 35 秒完整动画基线和 20 秒暂停骨骼播放样本。原生 `Eng-Render` 实际调度分别占单核 99.405% / 99.321%；应用帧中位 109.239 / 30.159 ms，P95 208.261 / 131.036 ms。用户确认暂停动画后仍很卡，不能作为修复；完整动画已在画板候选包中恢复。数据及限制见 [性能诊断](Stage-Performance-Diagnostics.md)，阶段墙钟不等于纯 CPU 执行时间。
- **2026-10-20 合批**：四种昆虫的同骨骼/同材质网格无损合批，保留全量顶点、UV、蒙皮、贴图和动画，图元 449→34；静态验证和 Blender 近景对照通过。完整动画、5 只昆虫下采集 20 秒：应用帧 P95 14.769 ms，原生 `Eng-Render` 单核 18.733%，不再满核；用户确认“卡顿明显减轻”。与旧基线昆虫数量、视角和热状态不同，不写成严格同条件提速比例。
- **剩余问题**：空间 GPUTime 平均 17.442 ms、P95 19.392 ms，仍超出 90 Hz 单帧预算，未完成 0/1/10 只与持续运行验收。因此标记“明显改善”，不标记“卡顿全部解决”。见 [1.0.10 交付](Stage-110-Delivery.md)。
- **后续原则**：对同一佩戴状态、相同昆虫数量、相同视角采集修改前后；分开看加载峰值、CPU、原生提交、GPU、合成器。避免一次混入降画质、关阴影、改模型和改输入，导致无法归因。
- **1.0.11 两轮探针**：默认 Auto 与 Fixed 投影均约 45 FPS、GPU 17–18 ms，Auto 距离缩到 2 m 仍为 45 FPS；均未改善，不保留。临时关闭主方向光阴影为 90 FPS / GPU P95 9.918 ms，但不把关阴影当作合格方案。随后只移除 opacity=1 的层级组件，阴影计数不变也达到 90 FPS / GPU P95 9.368 ms；挂回后仍 90 FPS，说明可能存在视角或原生缓存干扰，尚不能直接定根因。候选仅在渐变期间挂载透明度组件，撤去探针后做冷启动复验。逐次数据见 [1.0.11 性能](Stage-111-Performance.md)，10 只及长时间尚未验收。
- **1.0.11 后续失败与收尾**：保护接触面和动画的索引简化使阴影峰值三角形降至 1,515,744，但佩戴 40 秒仍为 GPU P95 19.125 ms，未达到目标。再改为隐藏 Shared Space 预览时释放灯光，阴影峰值仍为 334 次，未支持额外灯光 pass 假设；新采样混有零绘制/低帧率段，不能仅凭 GPU 均值降低宣布定因。用户实际确认“完全不卡顿”、HUD 约 46，并要求暂忽略帧率、优先绿色森林设计。记录为体验改善，帧率目标未达标；不追加诊断安装打断用户，保留基线与原始 trace。

## BW-07 · 高亮偏弱、交互意图不明确

- **1.0.9 实际结果**：用户确认昆虫会高亮，但不明显；捏合只选中蝴蝶/瓢虫，没有立即明显回应，用户不知道下一步操作与预期动作。
- **约束**：本地 `HoverEffectComponent` 无公开轮廓颜色/宽度配置；原生凝视反馈不能当应用可读取的眼动事件。不能用头朝向假冒眼动或把整虫换色说成描边。
- **候选实现**：明确捏合先有回应，再给短暂的目标附近提示；区分选中、靠近、落稳、离开和取消。5 项交互策略测试通过；提示的真机观感和操作清晰度尚未验收，原生高亮强度未改变。

## BW-09 · 表面穿插与返回跳变

- 环绕布局首个树干位置与叶片仍相交；BVH 检测发现 76 处三角交叠。移动树干后主要叶/木相交为零，旧失败报告已从最终资产目录清除，过程在此保留。
- 新路线由实际重导入 GLB 采样；37,716 个实际 Kotlin 地面样本距表面最大 3.044 mm。这只证明根位置贴面，不等于逐足 IK 或翅膀碰撞验证。
- 独立审查发现：触碰反应与手上停留结束同时发生时，临时“当前位置”目标可被误判为已返回家，继而跳回路线。改用真实 home 距离结束返回；复现旧条件时测试失败，修正后通过。

## BW-10 · 主窗口仍在，中央画板却不可见

- **现象**：1.0.9 诊断阶段，用户无法从画板进入花园；明确补充“顶部栏和画具可见，只有中间画板不见了”。
- **证据**：`Main.kt` 和 `PreviewScene.kt` 与用户确认的 1.0.8 相同，不能认定最近的透明度或天空修改直接改坏了画板。重启后日志显示画板 AttachmentPanel 创建、挂载成功且 enabled；但这不能证明最终可见。语义查询返回 `TARGET_ROOT_TIMEOUT`。
- **逐次诊断**：第一次加入挂载日志后用户仍看不到；再加入父节点 enabled 和生命周期日志并重启后，用户确认中央画板恢复。有效语义快照由 3 个根窗口变为 4 个，重新出现画纸、预览和去花园按钮。
- **排除过早结论**：画板坐标一直为 `(0,0,-0.2552)`，位于该 SpatialView 后边界内侧 0.8 mm；没有修改坐标就恢复，因此不能将后平面位置直接定为原因。曾计划的深度位置试验未执行。
- **SDK 线索**：6.1.0 会在 host `ON_PAUSE/ON_STOP` 禁用整个 SpatialView 根节点，只有 `ON_RESUME` 恢复。单独的画板 `enabled=true` 不证明祖先可见。恢复后的日志显示 host 为 RESUMED、祖先 enabled=true。目前没有捕获“应当可见但祖先仍禁用”的完整失败链，暂不加入人为强制启用或虚拟生命周期补丁。
- **首次恢复的检查**：新画纸确认后取消、作品册打开/关闭，画纸语义恢复/保持；弹出确认框时底下画纸从可访问节点隐藏属于正常遮罩行为。这些不替代持续佩戴下的视觉验收。
- **再次复发**：暂停动画诊断包冷启动后，用户再次看不到中央画板，通过作品册进入花园；用户明确不是从 Stage 返回时丢失。前一次恢复不构成修复，过早转去性能排查漏掉了连续冷启动回归。
- **候选处理**：等 host 第一次 `ON_RESUME` 后才创建 SpatialView/AttachmentPanel；等待时用普通 Compose 画板承接。首次前台之后不因每次暂停重新销毁画板，不强制覆写 SDK 根节点的 enabled。依据是失败启动时画板创建于 CREATED、父节点禁用，而成功时创建于 RESUMED；这是有证据的时序假设，仍不等于证实 SDK 内部根因。
- **候选检查过程**：两次启动日志均为首次挂载 active=true、父节点 enabled=true。但前两轮自动化在“新画纸”后的“取消”定位失败，没有完整通过；补充等待普通画板切换成独立原生面板后，下一轮在首个冷启动遇到 `TARGET_ROOT_TIMEOUT`，设备日志及 `dumpsys power` 确认已进入休眠。这三次尝试不能写成三次冷启动通过。
- **回归脚本**：`scripts/verify_studio_cold_start.py` 检查唤醒状态、独立画纸窗口、画纸/预览/去花园/画具语义，以及作品册打开关闭后画板保持。保留失败快照；脚本不删除保存的作品。仍需连续三轮通过以及用户视觉确认；Stage 返回是另一个检查，不混入冷启动结论。
- **最新结果（2026-10-20）**：用户明确确认“画板修复了”。将画板可见性标记为用户真机确认恢复；此前未完成的三轮自动检查仍保留原结果，不追认通过。本轮不改动这项修复。

## BW-11 · “送到大自然”后看不到新作品

- **现象**：用户在画板涂色后进入 Stage，没有看到新创作昆虫。
- **证据**：2026-10-20 设备日志两次记录 `Arrival started`，同一蝴蝶作品已完成保存/入园，最近保存为 revision 2，花园持久列表也包含该作品。出生位置却为 `(0.3759,0.9174,+1.7612)`。花园以进入时朝向为 -Z 前方，故生成在身后；保存链路失败并不符合这次记录。

## BW-21 · Stage 切换与手掌接触（2026-11-04，进行中）

## BW-22 · 多居民共享出生点和闭环（2026-11-04，待真机确认）

- **版本与现象**。1.0.12 的叶面小圈直径为 17 cm，倒木小圈宽约 5–9 cm。四种昆虫在花园内的归一化水平跨度为 26.4–43.2 cm。同种居民挤在一个这样的圈里行走，很难拉开身位。旧行为中独角仙一直爬行，蝴蝶直接起飞，毛毛虫每圈固定停住。
- **地面采样**。先沿批准的森林 GLB 采样一条倒木引导线，第 27 段的内插射线遇到凹口，采样拒绝输出。随后允许在引导线两侧小幅绕行，每段复测原网格上的端点及 1/4、1/2、3/4 位置。最终 11 条路线的最大插值离面小于 3 mm，叶面法线对 1.35 m 观察点的朝向点积全部为正。
- **飞行与间距**。首轮蝴蝶曲线使用同一升降通道，有一对同路居民中心只相距约 0.116 m。单独延迟横移仍有约 0.135 m 的靠近。将升、降分别安排在环线两侧，再按栖点确定出发方向并平滑起降。瓢虫飞行向叶缘侧移，避开叶心的蝴蝶出生区。最终以实际 Kotlin 路线每圈取 2,000 个相位，不同路线分别取 240 个独立相位比较。共享路线上的居民中心距均大于该物种归一化水平跨度加 2 cm。
- **放行与回归**。优先选空路线，再等公共时钟中的空相位经过出生点。居民出生、触碰、上手及归程期间，同路线保留相位。10 项 Kotlin 专项测试通过，涵盖四种十只同种组合、额满替换、重复放生和原点闭合。专项脚本起初因手势文件引入 SDK 姿态类型而无法独立编译，提取原有纯 Kotlin 的 HandPoint 后通过。
- **冷启动回归**。复查发现若优先给新作品分配路线，每次重建 Stage 时新作品都会拿到前方出生点。现改为先按已保存的花园顺序分配既有居民，再加载并放行新作品。逐次冷启动放生十只同种居民的测试确认，各自先占空路线，复用时按到达顺序等候。
- **未完成**。地面检查针对接触原点，中心距抽样没有验证整只动画虫体、翅尖、树皮遮挡和手掌访问自由路线。头显中的足部贴面、十只居民的画面及帧率、放生特效和着色均须实测。[路线记录](visual-redesign/2026-11-04/Routes.md)
